THREE PROJECTS / HOW AI WAS APPLIED

실제 프로젝트에서 AI를 어떻게 사용했는가

01REAL-TIME ETHERCAT / ROOT CAUSE SEPARATION

회전 위치 이벤트 기능의 실시간 오류 원인 분리

정상적인 동시 접근 경합과 실제 EtherCAT 수신 실패를 같은 오류로 취급하던 경로 분석

하네스를 적용한 방식100µs/1ms 실시간 제약과 안전 차단 조건을 먼저 고정한 뒤 수정

초기 가설을 그대로 확정하지 않고 첫 수정 뒤에도 증상이 재발하자 fault reason을 다시 분리했습니다. 정상 lock 경합과 실제 통신 실패가 같은 카운터에 합쳐지는 경로를 추적했습니다.

AI를 구체적으로 사용한 업무
  • 주기 내 lock 획득 실패로 snapshot 게시를 건너뛴 경우와 실제 Rx frame 실패를 분리
  • 정상 lock-skip에서는 gap counter를 증가시키지 않고, 실제 통신 실패의 안전 차단은 유지하도록 수정

실제 결과물 정상적인 Lock 경합은 오류 누적에서 제외하고, 실제 EtherCAT Rx/WKC 실패에 대한 안전 차단은 유지하도록 오류 판정 로직을 분리했습니다.

02LEGACY ETHERNET / INDEPENDENT STATIC REVIEW

Loader·DPRAM 변경 독립 정적 검토

이미 존재하는 통신 변경을 Codex가 읽기 전용으로 독립 검토

하네스를 적용한 방식활성 도구를 Codex로 제한하고, 구현과 독립 검토를 구분

제품 변형·빌드 가능 여부·증거 수준을 프로젝트 정책에 기록하고, 읽기 전용 검토 역할이 기존 Loader/DPRAM 변경의 요청 판정·busy 처리·통신 경로를 확인하도록 구성했습니다.

AI를 구체적으로 사용한 업무
  • 진행 중인 DPRAM 요청을 busy로 판정하는지와 다른 요청 상태를 지우지 않는지 소스 대조
  • Loader 수신 전에 DPRAM busy 상태를 확인하는 흐름과 관련 정적 검사를 확인
  • packet 자료의 Loader read와 다운로드 명령을 구분해 통신 분석 범위를 명확히 정리

실제 결과물 Loader 수신 전에 DPRAM busy 상태를 확인하고 진행 중 요청을 보호하는 흐름을 정적 검토해, 요청 충돌 방지 로직의 핵심 경로를 확인했습니다.

03MULTI-AXIS MOTION / HARNESS · DEBUGGING

다축 모션 하네스와 동시기동 연속운전 결함 분석

EtherCAT·PLC·통신·QA 역할을 분리한 Claude Code 하네스를 모션 오류 분석에 적용

하네스를 적용한 방식도메인 에이전트 5개와 스킬·품질 hook을 프로젝트 폴더 내부에 구성

Linux PLC 환경에서 EtherCAT Master와 PLC 런타임의 역할·소유 범위, 1ms 주기, DPRAM 양측 호환, 레거시 인코딩 규칙을 프로젝트 지침에 고정했습니다.

AI를 구체적으로 사용한 업무
  • 동시기동 준비 중 공유 위치·속도 값이 덮어써질 수 있는 경로를 추적하고 실행 전 로컬 복사로 보호
  • 한 축 완료 시 다른 축까지 정지되던 완료 처리를 분리해, 각 축 독립 완료 후 마지막 축에서 다음 연속 스텝으로 이동하도록 수정
  • 소프트 리밋 단위 혼용과 위치 변환·저장 순서 등 주변 모션 경계 조건도 함께 분석

실제 결과물 동시기동 실행 전 축별 목표 위치·속도를 보호하고, 한 축의 완료가 다른 축을 강제 정지시키지 않도록 완료 처리를 분리해 연속운전 흐름을 개선했습니다.
